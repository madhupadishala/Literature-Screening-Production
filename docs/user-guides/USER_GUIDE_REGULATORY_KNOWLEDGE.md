# User Guide — Regulatory Knowledge Administration

Document ID: UG-PV-KNOW-001  
Version: 1.0-draft  
Status: Sprint 1 — describes currently released/implemented administration concepts only; future UI steps shall be added after UI release.

## 1. Purpose
This guide explains how authorized personnel govern regulatory knowledge used by Nexus. It does not replace the source regulator document or qualified regulatory interpretation.

## 2. Audience
- Regulatory/PV reviewer
- Knowledge administrator
- Quality approver
- Validation/QA reviewer
- Auditor

## 3. Core concept
A source passes through controlled stages:

```text
Catalogued
 -> Acquired
 -> Parsed/Normalized
 -> Reviewed
 -> Chunked
 -> Approved
 -> Embedded/Indexed
 -> Production-eligible retrieval
```

A source shown as **Catalogued** is only registered. It must not be interpreted as fully loaded, reviewed or available for production decisions.

## 4. Regulatory source catalog
The source catalog is stored under:
`knowledge/Regulatory/regulatory-source-catalog.json`.

For each source, verify:
- source ID;
- authority;
- jurisdiction;
- title;
- canonical official URL/reference;
- lifecycle status;
- module/domain scope;
- ingestion status;
- version/effective date where known.

Do not replace an official URL with a blog, training site or vendor summary.

## 5. Adding a regulator/source
1. Confirm the source comes from an official regulator/harmonised body.
2. Assign a stable source ID.
3. Record jurisdiction and authority.
4. Record title and canonical URL.
5. Record version/revision, publication date and effective date when available.
6. Set `ingestionStatus` to `CATALOGUED` until acquisition actually succeeds.
7. Add applicable module/domain tags.
8. Submit the change through controlled Git review.
9. Do not mark production eligibility before regulatory/quality approval and validation evidence.

## 6. Source acquisition
When an acquisition workflow is released:
1. retrieve from the catalogued official source;
2. retain the original artifact where licensing/copyright policy permits controlled internal storage;
3. calculate SHA-256;
4. record acquisition timestamp;
5. compare with the previously approved artifact;
6. if changed, route for impact assessment rather than silently replacing the approved version.

## 7. Reviewing parsed content
Reviewers should verify:
- title and document identity;
- section/heading reconstruction;
- page/section citation fidelity;
- tables, footnotes and exceptions;
- warnings generated by parsers;
- missing/garbled content.

If material meaning is lost, do not approve the parsed version.

## 8. Reviewing chunks
A good regulatory chunk should:
- preserve the rule and directly relevant qualifier/exception;
- point back to the correct document/section/page where available;
- contain authority/jurisdiction/version metadata;
- not combine unrelated sections;
- not omit context that reverses or conditions the meaning.

Reject a chunk if citation fidelity or meaning is uncertain.

## 9. Embeddings and indexing
Embeddings are search representations, not the authoritative source.

Administrators shall verify:
- approved embedding model;
- expected vector dimensions;
- source/version association;
- index health;
- successful rebuild after material model/index changes.

## 10. Retrieval review
For regulated use, verify that results show:
- source title;
- source/version;
- section/reference;
- current/effective status;
- jurisdiction;
- relevant controlled content.

If the system reports no approved controlled context, the user must not treat an LLM-generated statement as regulator-backed evidence.

## 11. Jurisdiction differences
Do not merge conflicting regulator requirements into one generic instruction.

Record separate jurisdiction-specific rules and escalate ambiguous interpretation to qualified PV/regulatory review.

## 12. Superseded guidance
Never delete a superseded version merely because a new one exists when historical traceability is required.

Mark the lifecycle correctly and ensure current production retrieval favors/filters to effective approved material, while historical retrieval remains possible when justified.

## 13. AI use
AI may:
- help locate relevant sections;
- summarize controlled content;
- support structured extraction;
- identify potential impact areas.

AI shall not:
- change source text;
- invent a citation;
- decide that an unofficial source is authoritative;
- become the sole final authority for regulated PV decisions.

## 14. Troubleshooting

### Source appears but no search results
Check whether it is only catalogued, not acquired/approved/indexed.

### Wrong regulator/jurisdiction
Check folder/catalog authority metadata and source record.

### Citation points to wrong section
Stop production use of the affected parsed/chunked object and route for correction/revalidation.

### Embedding dimension mismatch
Rebuild using the approved embedding model/index configuration; do not mix dimensions.

### New regulator revision published
Create/update the catalog record, preserve the prior version, acquire/checksum the new version, and open an impact assessment.

## 15. Known Sprint 1 limitations
- The source catalog is intentionally not equivalent to a complete downloaded global corpus.
- Some regulator content may require manual acquisition, translation, access controls or copyright/licensing review.
- Qdrant/Elasticsearch unified production retrieval is a target shared capability; existing controlled retrieval paths remain until migration is validated.
- Module-specific regulatory interpretation is finalized in the respective module sprint.

## 16. Audit expectation
An auditor should be able to answer:
- Which regulator/version supported this requirement?
- Was that version effective at the relevant time?
- Who approved the knowledge for production?
- What exact chunk/citation was retrieved?
- Which model/index version was used?
- What changed when the regulator updated the source?
